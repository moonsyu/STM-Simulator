# 장치 외 기능 점검 — 개발용 수정 인계

점검일: 2026-10-15. 기준: v0.20.0 이후 부품 미리보기 작업 트리. Windows x64 / Electron 44.2.0.

이 문서는 사용자에게 코드 위치를 나열하지 않고도 후속 작업에서 바로 수정할 수 있도록 보관하는 개발 기록이다. 아래 4건은 **재현 완료·미수정** 상태다. 이번 요청에서 수정한 것은 부품 검색 이미지이며, 저장/터미널 코드는 변경하지 않았다. 라인 번호가 이동하면 함께 적은 함수/검색 문자열로 찾는다.

## 재현 실행

```powershell
node scripts/audits/non-device-repro.cjs
```

실제 Electron 창과 독립 테스트 프로필, 임시 프로젝트 폴더를 사용한다. 사용자 파일을 변경하지 않으며 테스트가 만든 폴더만 검증 후 정리한다. 첫 항목만 파일 잠금에 해당하는 `EACCES`를 한 번 주입한다. 나머지는 실제 UI/IPC 경로로 재현한다. 결과는 `work/test-results/non-device-audit.json`이다. 이 스크립트의 assertion은 **현재 결함을 재현했는지** 확인하므로 일반 회귀 검사/CI에 넣지 않았다. 결함 수정 후에는 올바른 동작을 확인하는 회귀 검사로 전환한다.

## AUDIT-01 — P1: 저장 중 실패하면 파일 내용이 서로 달라지고 재저장도 차단됨

- 재현: 프로젝트 폴더 생성 → 코드 변경 → `main.c` 교체 시 파일 잠금 오류 주입 → 다시 저장 → 프로젝트 다시 열기.
- 실제: `project.stm32lab`은 새 코드, `main.c`는 이전 코드로 남는다. 재저장은 앱 자체 변경을 외부 수정으로 오인해 거부한다. 다시 열면 `main.c`가 우선되어 이전 코드를 읽는다.
- 영향: 디스크에 일관되지 않은 프로젝트가 남고 저장 재시도로 복구할 수 없다. 화면의 최신 코드를 따로 보존하지 않고 다시 열면 최신 코드가 사라질 수 있다.
- 위치: `desktop/workspace.cjs:28` `saveWorkspace`; 32행의 파일별 write/rename, 34행의 마지막 hash 갱신. 다시 열 때는 24~25행 `openWorkspace`.
- 원인: 각 파일 rename은 개별 원자적이지만 프로젝트 전체는 원자적이지 않다. 앞 파일을 갱신한 뒤 뒤 파일에서 실패하면 기존 hashes와 디스크가 달라진다.
- 수정 방향: 변경/삭제할 파일 전체를 먼저 준비하고 원본 백업/저널과 rollback을 둔다. 실패하면 기존 파일 세트와 state를 복원한다. 사용자 외부 변경 감지는 유지한다. 프로세스 중단까지 다루려면 열기 시 미완료 트랜잭션 복구도 필요하다.
- 회귀 조건: 두 번째 파일 write/rename 실패, 보조 파일 삭제 실패, 재시도, 앱 재시작 복구에서 전체가 이전 상태 또는 새 상태여야 한다. 임시 파일/백업 정리와 외부 변경 보호를 함께 검증한다.
- 임시 대응: 저장 오류가 나면 최신 편집 내용을 별도 파일에 먼저 보존한다. 원본을 다시 열기 전에 내용을 비교한다.

## AUDIT-02 — P1: 빠르게 저장하고 다시 편집하면 미저장 경고가 생략됨

- 재현: 코드 변경 → 파일 저장 완료 → 첫 편집에서 1초 안에 다시 변경 → 새 프로젝트 생성.
- 실제: 파일에는 첫 번째 변경만 저장되어 있는데 변경 확인 창 없이 새 프로젝트 창이 열린다. 생성하면 두 번째 변경이 사라진다.
- 영향: 저장 직후 계속 입력하는 일반 편집 흐름에서 미저장 코드가 경고 없이 버려질 수 있다.
- 위치: `src/app.js:82` `checkpoint`, `src/app.js:350` `lastCodeCheckpoint`, 360행 코드 input, 371행 `save`, 345행 `requestReplace`.
- 원인: `dirty=true`가 Undo 스냅샷을 만드는 `checkpoint`에 결합되어 있다. 코드를 입력할 때 1초 단위로만 checkpoint를 생성하므로 중간 저장이 dirty를 지운 뒤 후속 입력이 dirty를 다시 켜지 않을 수 있다.
- 수정 방향: Undo 묶음 주기와 수정 여부를 분리한다. 모든 내용 변경에서 문서 revision을 증가시키고, 저장 시작 시 캡처한 revision과 완료 시 현재 revision이 같을 때만 저장 완료로 처리한다. 이렇게 해야 비동기 저장 도중 새 편집도 덮어 경고를 해제하지 않는다.
- 회귀 조건: 저장 직후 1초 이내/이후 편집, 저장 도중 추가 입력, 저장 취소/오류, 새 프로젝트·다른 프로젝트 열기 모두 최신 수정 여부에 따라 경고한다. Undo/Redo 그룹 동작은 유지한다.
- 임시 대응: 프로젝트 전환 전에 마지막 입력 뒤 파일 저장을 한 번 더 완료한다.

## AUDIT-03 — P2: 새 프로젝트의 터미널이 이전 프로젝트 폴더에서 시작함

- 재현: 프로젝트 폴더 A 열기 → 폴더 없이 새 프로젝트 B 생성 → 실행/터미널에서 터미널 시작 → `cd` 입력.
- 실제: UI는 `미저장 프로젝트`를 표시하지만 터미널의 현재 경로는 A다.
- 영향: 현재 프로젝트라고 생각하고 실행한 명령이 이전 프로젝트의 파일에 적용될 수 있다. 재현 검사에서는 읽기 전용 `cd`만 사용했다.
- 위치: `desktop/main.cjs:10` `workspaceState`, 49행 `terminal-open`, 62~64행 workspace IPC; `src/ide-ui.js:83` `reset`; `src/native-ide-ui.js:109` `reset`; `desktop/native-ide.cjs:49` `openTerminal`.
- 원인: 렌더러의 folder만 초기화하고 main 프로세스의 workspaceState는 이전 폴더를 유지한다. 기존 터미널이 열려 있으면 openTerminal도 그대로 반환한다.
- 수정 방향: 프로젝트 교체/생성/단독 회로 열기 시 main의 workspace 문맥을 명시적으로 갱신/해제한다. 기존 터미널의 작업 디렉터리를 표시하고, 프로젝트 전환 시 유지/재시작 정책을 정한다. 폴더 B 열기 직후 renderer reset이 새 main 문맥까지 지우지 않도록 전환 순서를 통일한다.
- 회귀 조건: A→미저장 B, A→폴더 B, A→단독 회로 파일, 터미널 실행/종료 상태 각각에서 표시된 프로젝트와 실제 cwd가 일치하거나 유지된 터미널 경로를 명확히 표시한다.
- 임시 대응: 명령 실행 전 `cd`로 현재 위치를 확인하고 원하는 폴더로 이동한다.
- 부가 관찰: 한국어 경로의 **첫 cmd 프롬프트**는 깨지고 `chcp 65001` 이후에는 정상이다. `openTerminal`이 UTF-8 디코더를 설정하기 전에 cmd가 기존 Windows 코드 페이지로 처음 출력하는 구간이 있다. 동일 재현 JSON의 terminalOutput에 기록했다. cwd 수정 시 첫 출력 인코딩도 함께 검증한다.

## AUDIT-04 — P2: 편집 직후 앱을 종료하면 마지막 편집이 자동 저장되지 않음

- 재현: 코드 A 입력 후 `자동 저장됨` 확인 → 코드 B 입력과 동시에 정상 창 닫기 → 같은 프로필로 앱 재실행.
- 실제: 코드 A가 복원되고 B는 사라진다. 강제 종료나 프로세스 kill이 아닌 정상 창 닫기로 재현했다.
- 영향: 마지막 입력 후 약 200ms 이내 종료하면 마지막 자동 저장 전의 상태가 복원된다.
- 위치: `src/app.js:81` `autosave`/`saveTimer`; `desktop/main.cjs:21` `before-quit`, 60행 `window-all-closed`; `src/app.js:406` 업데이트 전 저장 경로는 별도로 존재한다.
- 원인: 자동 저장 debounce를 정상 창 종료 시 비우지 않는다. main 종료 처리도 renderer의 최신 문서 저장 완료를 기다리지 않는다.
- 수정 방향: 창 닫기/앱 종료 경로에서 최신 문서를 확정 저장하는 공통 처리를 만든다. flush가 실패하면 실패를 보여주고 코드 보존 선택지를 제공한다. 업데이트 재시작 경로와 일반 종료 경로가 같은 문서 revision을 사용하도록 정리한다.
- 회귀 조건: 입력 직후 창 닫기·앱 종료·업데이트 재시작, main/보조 파일, 저장 공간 오류, 두 번 종료 요청에서 최신 내용 보존과 중복 종료 방지를 검사한다.
- 임시 대응: `자동 저장됨` 표시를 확인한 뒤 종료하고 중요한 작업은 파일로 저장한다.

위 정상 검사들은 성공 경로를 확인한다. 재현한 저장 실패·전환·종료 경계 조건까지 정상이라는 뜻은 아니다. 실제 보드 접속과 물리 ST-LINK/OpenOCD 디버깅은 이번에 실행하지 않았다. 실제 ARM 펌웨어를 회로 안에서 실행하는 CPU 에뮬레이션 미지원은 기존 제품 범위이며 신규 결함에 포함하지 않는다.
