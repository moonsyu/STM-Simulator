# 자동 업데이트

Windows x64 포터블 EXE는 앱 시작 8초 후, 이후 실행 중 6시간마다 GitHub의 최신 정식 릴리스를 확인합니다. 새 버전은 백그라운드에서 다운로드합니다. 상단 **업데이트** 버튼에서 진행 상태를 보고 자동 확인·다운로드를 끄거나 수동으로 확인할 수 있습니다.

다운로드가 끝나면 **저장 후 재시작**을 누르세요. 현재 회로와 모든 소스를 자동 저장하고, 폴더 프로젝트를 열어 두었다면 해당 폴더에도 저장합니다. 저장이 실패하면 앱을 종료하지 않습니다. 재시작할 때 기존 위치의 EXE를 교체하므로 바로가기와 파일명은 유지됩니다. 이후 배포 실행 파일명은 `STM-Simulator.exe`로 고정하며, 실제 버전은 업데이트 창에서 확인하세요. 폴더 프로젝트를 다시 열려면 기존 프로젝트 폴더를 선택하세요.

0.19.0 이하의 기존 배포본은 버전이 포함된 EXE 이름만 조회합니다. **0.20.0부터는 고정 파일명을 사용하므로 GitHub Releases에서 `STM-Simulator.exe`를 한 번 직접 다운로드해 실행해야 합니다.** 기존 EXE의 이름만 바꾸어서는 업데이트 조회 방식이 바뀌지 않습니다. 새 업데이트 코드는 고정 이름과 과거 버전별 이름을 모두 인식하며, 사용자가 실행 파일명을 바꾸어도 해당 경로에 업데이트를 적용합니다. 기존 릴리스 파일은 변경하지 않습니다.

0.15.2 이하에는 이 기능이 없습니다. **처음 한 번은 이 기능이 포함된 버전의 EXE를 직접 다운로드해야 합니다.** 개발 실행(`npm start`), 브라우저 실행, 포터블 런처를 거치지 않은 unpacked 앱에서는 자동 교체하지 않습니다. 인터넷과 EXE가 있는 폴더의 쓰기 권한이 필요하며, 관리자 권한 상승을 요청하지 않습니다.

## 파일 검증과 오류 처리

0.16.1~0.17.0의 공개 EXE 검사에서 다운로드/해시 검증 후 도우미 생성 시 `spawn EPERM`이 재현되었습니다. 새 버전은 `desktop/start-update.ps1`을 짧은 `-File` 인자로 실행하고, 파일 기반의 숨김 독립 프로세스에서 실제 교체를 수행합니다. 긴 경로와 실제 Electron GUI/ASAR에서의 도우미 시작을 별도 검사합니다. 이전 앱에서 도우미 실행에 실패하면 최신 EXE를 한 번 직접 다운로드하세요. 실패한 이전 앱의 회로와 코드는 그대로 유지됩니다.

- 고정된 `moonsyu/STM-Simulator` 저장소의 공개 정식 릴리스만 사용합니다. 앱에 GitHub 토큰을 넣지 않습니다. 초안·시험판·같은 버전·이전 버전은 적용하지 않습니다.
- `update-manifest.json`의 버전·파일명·바이트 수·SHA-256과 GitHub 자산 정보를 비교합니다. HTTPS 주소를 제한하고 다운로드 크기·연결 대기 시간을 제한합니다.
- 임시 파일 다운로드와 SHA-256 검증을 마친 뒤에만 적용할 수 있습니다. 적용 직전과 별도 Windows 프로세스에서도 다시 검증합니다.
- 다운로드 실패·오프라인·GitHub 요청 한도·쓰기 권한 오류는 기존 EXE를 유지하며 창에 표시합니다. 작업 중 강제로 재시작하지 않습니다.
- 별도 PowerShell 프로세스가 앱 종료와 포터블 런처의 파일 잠금 해제를 기다립니다. 같은 폴더에 새 EXE를 준비하고 원본을 백업하는 원자적 교체를 사용합니다. 새 실행 파일의 프로세스 시작에 실패하면 백업 복원을 시도합니다. 복원 실패 시 백업 파일을 남깁니다.
- 이는 앱의 정상 기동 완료를 확인하는 롤백 기능은 아닙니다. SHA-256은 전송 무결성을 검증하며 코드 서명을 대신하지 않습니다. Windows 보안 정책이 실행을 차단하면 릴리스에서 직접 내려받으세요.
- 사용자의 기존 `STM32 Circuit Lab` 프로필과 회로 자동 저장·개발 도구 설정을 유지합니다. 업데이트 설정은 프로필의 `updates/settings.json`에 저장합니다.

## 릴리스 게시

1. `package.json`과 잠금 파일의 버전을 올리고 검증·커밋합니다.
2. 해당 커밋을 `main`에 올립니다. Windows CI가 새 버전을 확인하고 `v<버전>` 태그와 Release를 생성합니다. 기존 커밋을 보충 게시할 때는 버전 태그 푸시도 지원하며 태그와 패키지 버전이 다르면 실패합니다.
3. Windows CI가 모델·업데이트 UI·실제 교체 도우미·기존 UI 테스트와 EXE 패키징 검증을 수행합니다.
4. `build:artifact`가 `STM-Simulator.exe`와 같은 빌드에서 `update-manifest.json`, `BUILD-INFO.json`, `SHA256.txt`를 만듭니다. 두 JSON의 `filename`과 체크섬의 파일명, ZIP 내부 실행 파일명도 `STM-Simulator.exe`입니다. 버전은 릴리스 태그와 JSON의 `version`으로 구분하며 ZIP 이름에는 버전을 유지합니다.
5. 게시 작업은 이 실행의 검증된 산출물만 내려받고 EXE 해시·크기·커밋을 확인합니다. ZIP을 만들고 EXE·ZIP·해시·빌드 정보·업데이트 매니페스트를 **초안 릴리스**에 모두 올린 다음 공개합니다.

`main`의 새 버전은 CI 전체 검사와 빌드가 성공하면 Release도 함께 공개합니다. 동일 버전의 후속 문서 변경은 기존 Release를 유지합니다. 선택적 부저 검사만 수행하는 푸시는 자동 게시하지 않습니다. 게시 작업을 직렬화하고 버전을 비교하여 과거 버전 보충 게시가 최신 Release를 낮추지 않도록 합니다. 게시 도중 실패하면 초안을 확인·정리한 뒤 재실행해야 합니다. 기존 릴리스가 있으면 자동 덮어쓰지 않습니다. 구버전에 업데이트 매니페스트가 없으면 새 버전으로 제공하지 않고 게시 미완료 오류를 표시합니다.

## 개발과 검증

- `node --test tests/updater.test.js`: 버전·자산·해시·동시 호출·오프라인·자동 설정·캐시 변조 검사.
- `npm run test:updates:ui`: 실제 Electron 창의 상태·설정·재시작 전 코드/폴더 저장·오류 처리·좁은 창 검사. IPC 응답만 테스트 내에서 대체하며 실제 앱을 교체하지 않습니다.
- `node scripts/update-apply-check.cjs`: Windows에서 실제 실행 파일 잠금을 기다려 교체·재실행하고, 잘못된 EXE의 시작 실패 시 원본 복원을 검사합니다.
- `LAB_EXE=... node scripts/update-gui-helper-check.cjs`: 패키징된 Electron main에서 실제 도우미를 시작하고, 긴 한글·특수문자 경로와 GUI 부모 종료 뒤 교체/실행을 검사합니다. CI 게시 전에 실행합니다.
- `npm run build` / `npm run build:artifact`: 업데이트 JS·PowerShell·UI·문서가 실제 패키지에 들어갔는지 원본과 비교합니다.

공개 서버를 통한 서로 다른 두 정식 앱 버전의 실제 업그레이드는 두 버전 게시 후 `node scripts/release-update-check.cjs`로 확인합니다. 이전 공개 EXE와 해시 증거(`work/test-results/update-release-baseline.json`)를 준비하고 실행하면, 자동 확인을 켜고 이전 앱의 원본 스케줄러가 GitHub 조회·다운로드·검증을 수행하게 합니다. 수동 확인·다운로드 메서드를 호출하지 않습니다. 이어서 저장 후 재시작과 실제 파일 교체를 수행하고, 새 프로세스의 asar 버전·파일 해시·실행 유지를 확인합니다. 새 앱을 다시 열어 코드·IDE 설정·보드 크기·자동 확인 설정 보존도 검사합니다. 이 검사는 업데이트 네트워크나 main IPC를 대체하지 않습니다.

실행 증거는 `work/test-results/release-update-proof.json`, 공개 배포 검증 증거는 릴리스 자산의 `UPDATE-VERIFICATION.json`으로 관리합니다.

기술 근거: [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release), [electron-builder v26 포터블 설정](https://www.electron.build/v26/docs/nsis/#portable), 빌드에 사용한 `app-builder-lib/templates/nsis/portable.nsi`의 `PORTABLE_EXECUTABLE_FILE` 환경 변수. 포터블 EXE는 표준 설치형 자동 업데이트 대상이 아니므로 현재 배포 형식에 맞는 별도 교체 과정을 사용합니다.
