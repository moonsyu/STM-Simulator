## 2026-10-21 · 0.32.0 NUCLEO-F103RB 보드 추가 (1단계: 회로 시뮬레이터)

- 요청: 연결한 NUCLEO-F103RB도 시뮬레이터에 추가하고, NUCLEO-F446RE와 같은 기능을 모두 쓸 수 있게.
- 실물 확인: 두 보드가 동시에 연결되어 있다. F103RB는 ST-LINK SN `0668FF544949878667173544`(FW V2J49M36, COM5), 장치 ID 0x410(medium-density). F446RE는 SN `0672FF485775495067192757`(COM6). 보드에 쓰거나 리셋하지 않았다.
- 범위 판단: F1은 F4와 핀 배치(AF 번호 대신 AFIO 리맵 묶음), DMA(스트림 대신 고정 채널), 클럭(64 MHz), ADC, 타이머 폭(모두 16비트)이 달라 단순 이름 교체로는 안 된다. 1단계로 회로 시뮬레이터 전체(보드·Pinout·코드 생성·인터프리터·예제)를 F1 규칙으로 만들고, 2단계 실제 ARM 빌드·실물 보드, 3단계 펌웨어 에뮬레이터로 나눴다.
- 구현: 계열 프로필 `233fa0a`, 보드·코드 생성·인터프리터 `6b21f8f`, F1 DMA·ADC 스캔·CAN 리맵 `3ffec6f`, 예제 자동 이식 `0b00910`, 보드 선택 UI `29ba47a`, 예제 목록·Pinout 요약 `b28f3c9`, F1 ARM 빌드 차단 `43a0026`, 문서 `6f4d5c2`.
- 예제: F446RE용 127개 중 125개가 F103RB에서 실행되고 124개는 출력이 F446RE와 같다. 다른 1개(ADC DMA 스캔)는 F1 ADC 변환 속도 차이로 블록 수만 다르다. DCMI 카메라·I2S 오디오 2개는 F103RB에 해당 주변장치가 없어 목록에서 빠진다. 이식 중 찾은 것: 32비트 TIM2 자유 카운터 예제 7개(16비트로 바꾸고 경과 시간을 `(uint16_t)`로), 한 줄에 여러 문장이 있는 DMA 초기화의 `Channel` 필드, CAN1 PB8/PB9(F1 리맵 2).
- 검증: `npm test` 697개 중 694 통과·1 건너뜀(실패 2개는 기존과 같은 로컬 심볼릭 링크 권한). E2E 24개 중 23 통과·1 건너뜀(뒤쪽·다크 임시 변경으로 실행, 끝난 뒤 되돌림). 앱에서 보드를 F103RB로 바꿔 보드 그림(Cortex-M3), Pinout(STM32F103RB · LQFP64 · Cortex-M3, USART 3개·TIM2/3/4), 예제 목록 125개, DMA UART 에코 예제 실행(DMA1 Channel6/7)을 확인했다.
- 남은 사항(2단계 이후): STM32CubeF1 HAL 다운로드(사용자 허락 필요), cortex-m3 빌드, OpenOCD에서 두 ST-LINK 중 보드 선택, 실물 F103RB 쓰기·실행 확인, F1 펌웨어 에뮬레이터.

## 2026-10-21 · 0.30.1 IDE에서 실물 보드 실행이 안 되던 문제

- 요청: 실행 환경을 무엇으로 해야 하는지, IDE로는 안 된다.
- 답: 실행 환경은 **STM32 · ARM GCC**. 개발 도구가 채워져 있어야 하고, 보드 연결에서 OpenOCD 자동 시작과 "시작할 때 빌드한 펌웨어를 보드에 기록"을 체크한다.
- 사용자 진단 로그(`%APPDATA%\STM32 Circuit Lab\diagnostics\events.jsonl`) 확인: 0.29.2에서 ARM GCC 미설정, 0.30.0에서 "STM32CubeF4 SDK 루트 폴더를 선택하세요"(SDK는 03:17에 이미 설치됨). 직후 개발 도구를 저장한 기록(04:10:58)이 있었다.
- 원인 1: 개발 도구 저장(`configure`)이 빈 항목을 자동 감지하지 않아 재시작 전까지 비어 있었다. 원인 2: 0.30.0에서 찾게 된 CubeIDE의 OpenOCD(ST 빌드)가 스크립트 경로 없이 `interface/stlink.cfg`로 시작해 바로 실패했다(`Can't find interface/stlink.cfg`, 경로를 줘도 `Infinite eval recursion`). ST 스크립트와 `stlink-dap.cfg`·`dapdirect_swd`로 OpenOCD가 STM32F446을 찾고 GDB 포트를 여는 것을 확인했다.
- 수정과 확인: 두 원인을 고치고, IDE의 ▶과 같은 `NativeIde.run` 경로로 빌드·OpenOCD·플래시·실행을 실물 보드에서 확인했다(`uwTick` 실시간 증가, PA5 변화). 단위 테스트 2개 추가. 확인 뒤 보드에는 버튼 토글 펌웨어를 다시 썼다.
- 검증: `npm test` 683개 중 680 통과(실패 2개는 로컬 심볼릭 링크 권한).

## 2026-10-21 · 실물 NUCLEO-F446RE에 예제 쓰기

- 요청: LED 점멸 예제를 보드에 써서 동작 확인(기존 펌웨어 삭제 허락), 이어서 버튼으로 LED를 토글하는 예제를 빌드해 쓰고 확인.
- LED 점멸(`blink`): 앱의 실제 ARM 빌드 경로(`native-build.cjs`, CubeIDE GCC 13.3.1, STM32CubeF4 v1.28.3)로 빌드해 STM32_Programmer_CLI로 0x08000000에 20.58 KB를 쓰고 검증(`Download verified successfully`)한 뒤 리셋했다. 실행 중 SWD 핫플러그로 `GPIOA->ODR`(0x40020014)을 읽어 PA5(LD2)가 0→1로 바뀌는 것을 확인했다(약 470 ms 시점). 링크 경고 `_lseek`/`_read` 미구현은 newlib 기본 스텁 경고로 이 펌웨어와 무관하다.
- 토글 주기를 더 길게 재는 도중 ST-LINK가 `DEV_USB_COMM_ERR`로 응답하지 않게 됐다. 장치는 Windows에 보이고 ST-LINK를 잡은 프로그램·서비스는 없었다. USB를 다시 꽂아야 풀린다.
- 버튼 토글: 보드 USER 버튼(B1, PC13) EXTI로 누를 때마다 LD2(PA5)를 전환하는 `exti` 예제를 같은 경로로 빌드했다(배선 불필요). ST-LINK가 복구되면 쓰고, PC13 EXTI 설정과 버튼을 눌렀을 때 ODR 변화를 확인한다.
- 사용자가 USB를 다시 꽂은 뒤 ST-LINK가 정상 연결됐다. `exti` 펌웨어 20.92 KB를 쓰고 검증·리셋했다.
- 실물 확인(SWD 핫플러그, 연결 횟수를 줄여 한 세션에 묶음): `SYSCFG_EXTICR4`가 EXTI13을 GPIOC로 연결(2), `EXTI_IMR`·`EXTI_FTSR` 13번 비트 1(하강 에지), NVIC `EXTI15_10`(IRQ40) 활성, PC13 대기 레벨 1(버튼 놓음). `EXTI_SWIER`로 EXTI13을 두 번 발생시켜 실제 인터럽트 처리기가 PA5(LD2)를 0→1→0으로 바꾸고 `EXTI_PR`을 지우는 것을 확인했다. `-w32`의 "Failed to download data"는 SWIER가 처리 후 스스로 0이 되어 쓰기 후 읽기 확인이 어긋난 것이며 쓰기는 적용됐다.
- 물리 버튼을 사람이 누르는 확인은 사용자에게 맡겼다(누를 때마다 LD2가 켜졌다 꺼짐).
- 빌드·플래시 스크립트는 세션 scratchpad `board/build-blink.mjs`(예제 ID 인자)이며 저장소에는 넣지 않았다.

## 2026-10-21 · 0.29.2 코드 정렬이 한 줄의 여러 문장을 나눔

- 요청: 코드 정렬이 들여쓰기(tab)만 고치고, `uint8_t bank[1]={1}, id[2]={0};if (…) {…;printf(…);} else printf(…);HAL_Delay(1000);` 같은 한 줄은 그대로다. 목표 형식은 문장마다 한 줄, `} else {` 중괄호, 연산자 공백은 그대로.
- 원인: 내장 정렬기(`formatC`)가 중단점·`USER CODE` 표식을 지키려고 줄 수를 바꾸지 않도록 만들어져 있었다.
- 수정: `formatCode`가 문장마다 줄을 나누고 들여쓰며, 중괄호 있는 갈래 뒤의 `else` 한 문장에 중괄호를 붙인다. 편집기는 원래 줄 단위로 바꿔 중단점이 문장을 따라가고, 저장 시 정렬은 중단점 줄을 다시 계산한다. 사용자가 준 목표와 글자 단위로 같은 결과를 단위 테스트와 실제 앱 E2E로 확인했다.

## 2026-10-21 · 0.29.1 `}` 자동 정렬 수정과 예제 코드 정리

- 요청: 중괄호 입력 시 자동 정렬이 동작하지 않는다, HAL 예제 코드가 한 줄로 몰려 있다, 테스트 창은 다크 모드로.
- 원인: `}` 정렬이 키 이름(`}`)으로 감지했는데 Windows 한글 IME에서는 키 이름이 `Process`로 온다. 기존 E2E는 `keyboard.type`으로 실제 `}` 키를 보내 통과했다. `keyboard.insertText('}')`로 IME 입력을 재현해 실패를 확인한 뒤, Monaco `onDidType`으로 바꿔 통과시켰다. 자동 닫힌 `}` 덮어쓰기도 함께 검사한다.
- 예제 정리: 54개 예제의 187줄에 여러 문장이 몰려 있었다. `expandC`로 한 줄에 한 문장씩 나누고 들여쓰기를 다시 계산한다. 127개 모두 토큰 불변·멱등을 단위 테스트로 확인했다.
- 테스트 창: 작업 중에는 다크 모드·비활성·맨 뒤로 여는 임시 변경을 쓰고 끝난 뒤 되돌렸다(커밋하지 않음). 메모리에도 기록했다.
- 검증: `npm test` 678개 중 675 통과(실패 2개는 로컬 심볼릭 링크 권한), E2E 21개 중 20 통과·1 건너뜀.
- 커밋: `6e53b25` `}` 정렬 IME 수정, `1728566` 예제 코드 정리, `3be9c02` 0.29.1 버전.
- 첫 CI [39527156197](https://github.com/moonsyu/STM-Simulator/actions/runs/39527156197) 실패: E2E에서 편집 메뉴의 "코드 정렬"에 단축키가 비어 있었다. 메뉴가 단축키·위치를 `toggle` 이벤트(메뉴가 이미 보인 뒤 비동기)에서 채워서 생긴 경쟁 상태다. 사용자에게도 잠깐 빈 단축키·이전 위치로 보일 수 있었다. `beforetoggle`에서 채우도록 고치고 로컬 E2E를 두 번 연속 통과했다. Release·태그는 만들어지지 않았으므로 같은 버전 0.29.1로 다시 게시한다.
