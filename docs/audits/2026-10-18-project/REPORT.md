# STM Simulator 0.23.8 상태 분석

점검일: 2026-10-18. 대상: `D:\codex\project\STM-Simulator`, 커밋 `dc999bfc55f42664aa58968c320abaeab847e8c4`, Windows x64.

이 문서는 **발견·재현 결과**입니다. 제품 코드나 사용자의 회로를 수정하지 않았습니다. 분석용 스크립트와 기록만 추가했습니다. 구체적인 소스 위치와 수정 순서는 별도 개발 인계 문서에 보관합니다.

가장 먼저 해결할 문제는 저장 실패와 빠른 편집에서 발생하는 **코드 유실**입니다. 기본 장치 예제가 통과해도 C 연산의 정확성, 초기화 후 변형된 회로의 재적용, 실제 공개 ZIP의 업데이트까지 정상이라는 뜻은 아닙니다.

## 확인한 문제

P1은 코드 유실 등 우선 수정 대상, P2는 특정 조건에서 기능이나 결과가 잘못되는 문제, P3은 안내·검증 체계의 불일치입니다. 의존성 권고의 심각도는 제품 결함 우선순위와 별도로 표시합니다.

## C 실행 결과 비교

각 코드를 실제 Windows GCC와 앱의 HAL 인터프리터에 실행했습니다. 대상 ABI에 민감한 구조체 크기는 ARM GCC의 Cortex-M4 정적 검증으로도 8임을 확인했습니다. undefined behavior에 의존하는 사례를 의도적으로 사용하지 않았습니다.

| 검사 | 실제 C | 앱 |
|---|---:|---:|
| `struct { float v; uint16_t raw; }` 크기 | 8 | 6 |
| i=1에서 `sizeof(i++) * 100 + i` | 401 | 402 |
| double x의 `sizeof(x + 1)` | 8 | 4 |
| float 배열을 가리키는 p의 `p[0] / 2` | 2.5 | 2 |
| 중첩 구조체의 float 필드 / 2 | 2.5 | 필드 접근 오류 |
| uint8_t 구조체 필드를 300으로 초기화 | 44 | 300 |
| 구조체 배열의 float 필드 / 2 | 2.5 | 2 |
| `(1.0 < 2.0) / 2` | 0 | 0.5 |
| uint32_t `0x80000000U >> 1` | 1073741824 | -1073741824 |
| uint32_t UINT32_MAX와 int -1 비교 | 같음 | 다름 |
| uint32_t UINT32_MAX + 1U를 double에 저장 | 0 | 4294967296 |
| `010` | 8 | 10 |
| `enum { A=1<<3, B }`의 B | 9 | 파싱 오류 |
| int 함수가 3.5 반환 | 3 | 3 · 정상 대조군 |

실제 C 14조건 중 13조건이 달랐습니다. 실패가 예상되는 조건을 골라 검사한 수치이므로 전체 C 지원의 실패율로 해석하면 안 됩니다. 별도 변환기 2조건과 대표 라벨 재적용 3조건까지 포함한 비교 기록은 19조건 중 18차이를 보입니다.

## 배포 파일 확인

- main과 최신 태그는 모두 위의 기준 커밋이며 최신 릴리스 표시는 v0.23.8입니다.
- 공개 포터블 EXE와 ZIP을 실제 내려받아 SHA256.txt와 대조했습니다. 둘 다 일치하고 ZIP의 CRC도 정상입니다.
- ZIP 내부의 주요 앱 소스는 현재 커밋과 일치했습니다. 130개 비교 항목 중 121개가 일치하며, 나머지는 패키징 시 변환되는 package.json과 번들로 대체되는 테마 원본 8개입니다. 이것을 앱 코드가 구버전이라는 근거로 사용하지 않았습니다.
- 공개 포터블과 ZIP 앱을 각각 독립 프로필로 시작해 버전·업데이트 상태·구조체 크기 계산을 확인했습니다. 사용자의 실행 파일 교체나 실제 업데이트 설치는 하지 않았습니다.
- 배포 문제는 **ZIP 형식과 자동 업데이트 불가, 출처 메타데이터 누락**입니다. 이번 결과로 바이너리 변조나 구버전 코드라고 단정하지 않습니다.

## 의존성 점검

높음 경고는 빌드 도구 하위의 brace-expansion과 http-cache-semantics입니다. 각각 중첩 패턴 처리 DoS, 공유 캐시 응답 노출에 관한 공개 권고와 대조했습니다. 이 앱에서 해당 공격 조건이 충족되는지까지 입증한 것은 아닙니다. [brace-expansion 권고](https://github.com/advisories/GHSA-qhr7-859c-m2p7), [http-cache-semantics 권고](https://github.com/advisories/GHSA-ch52-4w7c-c8xp).

Monaco에는 DOMPurify 3.4.15가 포함되므로 모든 경고를 “개발 의존성뿐”이라고 제외할 수 없습니다. 확인한 권고는 IN_PLACE 모드 등 특정 조건에 관한 것이며 현재 편집기 호출에서 그 조건을 재현하지 않았습니다. 의존성 갱신과 도달 가능성 확인이 필요한 상태입니다. npm의 자동 수정 제안에는 이전 major 계열로 되돌리는 제안도 있으므로 무조건적인 force fix는 적절하지 않습니다. [DOMPurify 권고](https://github.com/advisories/GHSA-p98j-92pf-mc4p).

## 사용 중인 앱 로그

사용자 진단 로그는 읽기만 했고 원본이나 사용자 코드를 이 문서에 복사하지 않았습니다. 현재 버전에서 PA0 비활성 사용 오류 2회와 수동 수정된 Docs 영역 보호 오류 3회가 보입니다. 둘 다 안내대로 잘못된 실행이나 코드 덮어쓰기를 차단하는 동작이며, 이 로그만으로 새로운 제품 결함으로 분류하지 않았습니다. 과거 이벤트의 코드와 최신 회로 사본은 동일하다고 가정하지 않았습니다.

최종 수치와 실행 로그 목록은 함께 저장한 `coverage.json`에 있습니다. 기존 323개 자동 검사, 기본 장치 114종 실행, 배선 제거 701건 복구, 초기화 128조건, 재적용 114종, 실제 네이티브 도구, 화면 대비, 공개 배포 파일을 검사했습니다. HAL 함수 카드는 각각 코드 삽입·도달·상태 반환을 검사하고, 장치 전체 예제는 장치별 출력 기준으로 별도 검사합니다. 모든 입력 조합이나 모든 카드의 모든 물리 동작을 검증했다는 의미는 아닙니다.

화면은 Dark/White 52상태의 HTML 글자 대비를 검사하고 두 테마의 실제 화면을 확인했습니다. 사용자 지정 코드 색상, 장치 그림 안의 모든 글자, 모든 화면 배율과 스크린리더까지 보증하지 않습니다. 현재 커밋의 Windows CI는 패널 이동·크기·검색·배선·단축키·USART2 등 검사 단계를 성공했으며, 그 사실과 이번 추가 재현 결과를 함께 기록했습니다.

물리 STM32 보드·ST-LINK 연결, 모든 Bare-metal 예제의 재컴파일, 인터넷을 통한 실제 버전 간 교체, 모든 의존성의 공격 가능성은 이번에 전수 검증하지 않았습니다. 실제 ARM 펌웨어를 회로 안에서 실행하는 CPU 에뮬레이션 미지원은 기존 제품 범위이므로 신규 버그 목록에 포함하지 않았습니다.

수정 순서는 A01/A02의 저장 보존 → A03/A04의 종료·프로젝트 문맥 → A05의 회로 중복 → C 실행 정확성 → 배포 ZIP·메타데이터 → 의존성·문서 정리가 적절합니다. 수정 후에는 이번 실패 사례를 정상 동작을 요구하는 회귀 검사로 전환해야 합니다.
